# RAG Pipeline

Ask questions about your own documents. You send text, Markdown or PDF files to an HTTP API; the stack splits them into chunks, stores them as vectors and answers questions with a local language model, citing the passages it used. No external AI service is involved.

## Architecture

| Service | Image | Port (host) | What it does |
|---|---|---|---|
| `rag-api` | `ghcr.io/aisolutionscamp/rag-api:1.0.1` (built from [`app/`](app)) | `127.0.0.1:8000` | `POST /ingest`, `POST /query`, `DELETE /documents`, `GET /health` |
| `qdrant` | `qdrant/qdrant:v1.20.0` | `127.0.0.1:6333` | Vector store; REST API and dashboard at `/dashboard` |
| `ollama` | `ollama/ollama:0.40.11` | `127.0.0.1:11434` | Runs the embedding model and the chat model |

How a request flows:

1. **Ingest**: rag-api extracts the text (PDF page by page), splits it into chunks of `CHUNK_SIZE` characters with `CHUNK_OVERLAP` overlap (breaking at paragraphs, lines or sentences where possible), embeds the chunks with `EMBED_MODEL` in Ollama and upserts them into the Qdrant collection `QDRANT_COLLECTION`. Each point stores `source`, `chunk`, `page` (PDF), `text`, `metadata` and `ingested_at`. Ingesting a source again replaces its earlier chunks.
2. **Query**: rag-api embeds the question, takes the `TOP_K` most similar chunks from Qdrant and asks `CHAT_MODEL` to answer only from them. The response contains the answer and the sources with their scores.

On its first start rag-api pulls both models into Ollama (about 2.3 GB with the defaults) and creates the collection with the vector size of the embedding model. `GET /health` returns 503 until that is done, so `docker compose up --wait` returns once the stack can answer questions.

Data lives in the named volumes `qdrant_data` (vectors) and `ollama_data` (models).

## API

All endpoints except `/health` and `/health/live` need the API key when `RAG_API_KEY` is set, as `X-API-Key: <key>` or `Authorization: Bearer <key>`. The OpenAPI description is at `/docs`.

```bash
KEY=$(grep ^RAG_API_KEY= .env | cut -d= -f2)

# Ingest files (.txt, .md, .pdf); the file name becomes the source
curl -s -X POST localhost:8000/ingest -H "X-API-Key: $KEY" \
  -F files=@handbook.pdf -F files=@notes.md

# Ingest text as JSON
curl -s -X POST localhost:8000/ingest -H "X-API-Key: $KEY" -H 'Content-Type: application/json' \
  -d '{"documents":[{"source":"faq","text":"Support is available Monday to Friday, 9 to 17.","metadata":{"team":"support"}}]}'

# Ask a question (optional: "top_k", and "source" to search one document only)
curl -s -X POST localhost:8000/query -H "X-API-Key: $KEY" -H 'Content-Type: application/json' \
  -d '{"question":"When is support available?"}'
# Response shape (answer text and score vary):
# {"answer":"...","model":"llama3.2:3b",
#  "sources":[{"n":1,"source":"faq","page":null,"chunk":0,"score":0.8,"text":"Support is ..."}]}

# Remove a document
curl -s -X DELETE "localhost:8000/documents?source=faq" -H "X-API-Key: $KEY"
```

## Configuration

Copy `.env.example` to `.env`. Every setting is commented there; the main ones:

| Variable | Default | Notes |
|---|---|---|
| `QDRANT_API_KEY` | none, required | `openssl rand -hex 32` |
| `RAG_API_KEY` | empty | Set it. Empty means no authentication on rag-api. |
| `EMBED_MODEL` | `nomic-embed-text:v1.5` | Any Ollama embedding model, e.g. `mxbai-embed-large`, `bge-m3` |
| `CHAT_MODEL` | `llama3.2:3b` | Any Ollama chat model, e.g. `qwen2.5:7b`, `llama3.1:8b` (more RAM) |
| `CHUNK_SIZE` / `CHUNK_OVERLAP` | `1000` / `200` | Characters |
| `TOP_K` | `4` | Chunks per question |
| `RAG_API_PORT`, `QDRANT_PORT`, `OLLAMA_PORT` | `8000`, `6333`, `11434` | Published on 127.0.0.1 |
| `RAG_API_BIND` | `127.0.0.1` | Set `0.0.0.0` only behind a firewall or a TLS proxy |

Changing `EMBED_MODEL` changes the vector size. rag-api then reports the mismatch on `/health` and does not start serving; set a new `QDRANT_COLLECTION` and ingest your documents again.

**GPU**: with an NVIDIA GPU and the NVIDIA Container Toolkit, start with the override file:

```bash
docker compose -f compose.yaml -f compose.gpu.yaml up -d --build --wait
```

**Published image instead of a local build**: `docker compose pull rag-api && docker compose up -d --no-build --wait`.

## Security notes

- Qdrant always requires `QDRANT_API_KEY`; compose refuses to start without it.
- Set `RAG_API_KEY`. Without it anyone who can reach port 8000 can read and change your documents.
- All ports are bound to 127.0.0.1. Ollama has no authentication, so never publish port 11434 to a network.
- rag-api runs as a non-root user with a read-only filesystem and no Linux capabilities.
- The API speaks plain HTTP. For access from other machines put a reverse proxy with TLS (Caddy, Traefik, nginx) in front, or use an SSH or SSM tunnel.
- Answers are generated by a language model and can be wrong. The returned sources let you check them.
- Telemetry: Qdrant telemetry is disabled (`QDRANT__TELEMETRY_DISABLED`).

## Deployment options

- **Docker Compose**: this directory, see `quickstart/docker.md`.
- **Kubernetes (Helm)**: the [`rag-stack` chart](https://github.com/aisolutionscamp/charts/tree/main/charts/rag-stack) deploys the same three services (Qdrant and Ollama as subcharts), generates the API keys and adds NetworkPolicies. See `helm/install.sh` and `helm/values.yaml`.
- **Terraform, Docker provider**: `terraform/local/main.tf` creates the same containers on one Docker host.
- **Terraform, AWS**: `terraform/aws/main.tf` creates one EC2 instance (CPU, optional GPU type) that runs this compose stack, with SSM Session Manager instead of SSH and rag-api reachable only from `allowed_cidr`.

## Upgrading

1. Read the release notes of the new Qdrant and Ollama versions.
2. Change the image tags in `compose.yaml` (or pull the new version of this repository) and run `docker compose up -d --build --wait`. Volumes are kept.
3. Back up Qdrant before major upgrades. Create a snapshot, then download it (snapshots are written inside the container, not to the volume):

   ```bash
   QK=$(grep ^QDRANT_API_KEY= .env | cut -d= -f2)
   curl -s -X POST -H "api-key: $QK" localhost:6333/collections/documents/snapshots   # prints the snapshot name
   curl -s -H "api-key: $QK" -o documents.snapshot localhost:6333/collections/documents/snapshots/<name>
   ```

Model upgrades: change `CHAT_MODEL` and restart rag-api; the new model is pulled on start. Old models stay in the volume until you remove them with `docker compose exec ollama ollama rm <model>`.

## Troubleshooting

| Symptom | Check |
|---|---|
| `up --wait` takes long on first start | rag-api is pulling the models: `docker compose logs -f rag-api` |
| `/health` returns 503, `detail` mentions the vector size | The embedding model changed; use a new `QDRANT_COLLECTION` (the log has the exact sizes) |
| `/health` detail `waiting for Qdrant and Ollama` | `docker compose ps`; Qdrant or Ollama is not healthy (`docker compose logs rag-api` shows the error) |
| `401 invalid or missing API key` | Send `X-API-Key` with the value of `RAG_API_KEY` |
| `502` with `Qdrant ... returned 401` | rag-api and Qdrant use different `QDRANT_API_KEY` values; recreate both containers |
| Query times out | CPU inference is slow for large models; use a smaller `CHAT_MODEL`, raise `LLM_TIMEOUT`, or use the GPU override |
| PDF gives no chunks | Scanned PDFs contain images, not text; run OCR first |
| `415 unsupported file type` | Only `.txt`, `.md` and `.pdf` are accepted |
